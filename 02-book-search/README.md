# 도서 검색 앱 (Book Search App)

Google Books API를 활용한 도서 검색 웹
검색어를 입력하면 관련 도서 목록을 표지·저자·출판일 표출 및 페이지네이션 지원

## 사용 기술
- React (Vite)
- JavaScript
- Google Books API

> 스타일(CSS)은 학습 범위가 아니므로 AI 구현본의 것을 그대로 사용함.

## 주요 기능
- 검색어 입력 시 자동 검색 (useEffect) -> App_useEffect.jsx
- 검색어 입력 시 버튼 검색 (이벤트 핸들러) -> App.jsx
- 로딩 / 에러 / 검색 결과 없음 / 결과 표시 상태 처리 (status 문자열 하나로 관리)
- API 호출 로직 분리 (api/googleBookApi.js)
- 도서 표지, 제목, 저자, 출판일 렌더링
- API 키 환경변수(.env) 관리
- 페이지네이션 (이전 / 다음)

## 실행 방법

```bash
npm install
npm run dev
```

API 키 없이도 동작하지만, 요청 할당량 제한(429)이 낮아 검색이 자주 실패할 수 있음.
키를 발급받은 경우, 프로젝트 루트에 .env 파일을 만들고 Google Books API 키를 설정 필요

```bash
VITE_GOOGLE_BOOKS_API_KEY=발급받은_키
```

## 트러블슈팅

### Google Books API의 totalItems 신뢰성 문제
- **증상**: `totalItems`가 검색어와 무관하게 부정확한 값(예: 300)으로 반환되고,
  다음 페이지 요청 시 값이 급변하며(300 → 3) `items`가 빈 배열로 오는 경우 발생.
- **원인**: Google Books API의 `totalItems`는 전체 개수가 아니라
  "현재 인덱스 기준 남은 항목의 추정치"라, 요청마다 값이 달라지고 신뢰할 수 없음.
- **현재 상태**: 원인은 확인했으나 별도 처리를 하지 않고 진행 중.
  마지막 페이지에서 빈 결과가 표시되는 문제가 남아 있음.
- **한계**: API 특성상 완벽한 전체 페이지 수 표시는 불가능하여,
  현재 페이지 번호만 노출하고 다음 페이지 유무는 응답 기반으로 판단함.
- **해결**: totalItems 기반 페이지 수 계산은 유지하되,
  빈 응답이 오면 현재 페이지를 그대로 두고 안내 문구만 출력하도록 변경.
  비어 있는 페이지 하나가 그 뒤 전체가 비었다는 뜻은 아니므로
  페이지 버튼은 줄이지 않고 유지함.
- **참고**: AI 구현본은 빈 페이지를 만나면 이전 페이지를 다시 요청하는 방식이었으나,
  되돌아간 페이지에서 페이지 수가 재계산되어 원래 값으로 돌아가는 문제가 있었음.


## 비교 전 예측

AI 구현본의 코드를 읽기 전에 예상되는 차이를 먼저 정리함.
단, 실행 화면과 폴더 구조는 이미 확인.

### 화면·구조에서 이미 확인한 것
- API 호출 로직이 별도 파일로 분리되어 있음
- 컴포넌트가 list / item / pagination / searchform / status로 분리되어 있음
- 페이지네이션 표시 방식이 다름 (내 구현 `1/30`, AI는 `1 2 3 4 5`)  
일반적인 검색 화면은 페이지 번호를 나열하는 형식이므로, 사용자 입장에서 AI쪽이 더 옳은 형태로 판단하여 변경 예정.
- 표지 이미지가 없을 때: 내 구현은 표시 생략, AI는 '표지 없음' 표기
- 검색 전 초기 화면: 내 구현은 안내 없음, AI는 안내 문구 있음

### 코드를 보기 전 예상
- **API 호출 위치** — fetch가 App.jsx 안에 그대로 있음. 01에서의 localStorage과 같이 분리 방식 확인할 것.
- **로딩·에러 처리** — 만들어 두긴 했으나 상태 컴포넌트(status)를 생성한 것을 보니 처리 방식이 다를 것으로 예상.
- **totalItems 처리** — 한계를 확인했으나 대응하지 않고 넘어감. 페이지 번호 나열 방식으로 변경 시, 전체 개수의 필요 문제 발생. AI는 해당 내용을 어떻게 처리했는지 확인 필요.

## 비교 결과

| 예측 | 결과 |
|---|---|
| API 호출 위치 — 별도 파일로 분리되어 있을 것 | ⭕ |
| 로딩·에러 처리 — 방식이 다를 것 | ⭕ |
| totalItems — 다르게 우회했을 것 | △ (대응 방식에 버그 있음) |

**API 호출 위치**
- api 폴더를 따로 생성. URL에 값을 직접 넣지 않고 params 형식으로 전달
- Google Books API에서 자주 발생하는 429(할당량 초과)를 별도 문구로 처리
- API가 여러 개가 될 경우를 생각하면 이렇게 구분해두는 편이 나아 보임

**로딩·에러 처리**
- 기존 코드는 loading / error / searchFlag를 각각 boolean으로 관리. 여러 개가 동시에 참이 되는 조합이 생겨 꼬일 여지가 있음.
- AI는 StatusMessage 컴포넌트로 분리 및 status 문자열 하나('idle' | 'loading' | 'error' | 'success')로 관리
- App.jsx가 길어지지 않아 코드가 정리되어 보임

**totalItems 처리**
- AI는 버튼 개수 상한(MAX_PAGES)과 빈 페이지일 경우 바로 앞 페이지로 되돌리는 방식으로 대응.
- 문제 1 : 3페이지가 비어서 2페이지로 되돌아갈 때, 2페이지에도 비어있으면 더이상 되돌리지 않고 결과 없음 출력.
- 문제 2 : 1페이지에만 데이터가 있다고 할 때, 2페이지를 누르면 빈 페이지이므로 1페이지를 다시 요청함. 이때 pageCount(페이지네이션 버튼 개수)를 1로 줄여놓은 값이 totalItems 기준으로 재계산되어 원래대로 돌아가는 버그.
- 페이지 번호 나열 방식은 가져오되, 이 부분은 수정해서 적용 필요.



### AI 점검으로 추가 확인한 것

Claude Code에 두 폴더 비교를 요청해 개선점 목록을 받아 발견하지 못한 것 중 반영하기로 한 항목:

- **검색어 URL 인코딩 누락** — 템플릿 리터럴에 검색어를 그대로 넣어
  `&`, `#`, 공백 등이 포함되면 쿼리 구조가 깨짐. URLSearchParams로 처리 필요.
- **volumeInfo 없는 응답 미고려** — 해당 필드가 없는 항목이 실제로 존재하는데
  바로 구조 분해해서 런타임 에러 발생 가능.
- **공백만 입력한 검색어** — `=== ''`만 확인해 스페이스바 입력이 그대로 통과됨.
